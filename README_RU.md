# icloud-synk

*In English: [README.md](README.md)*

Демон для Ubuntu (Go, без CGO), который держит указанную папку синхронной с iCloud:

* **iCloud Drive — двусторонне и на лету.** Положили файл в папку — он уехал в облако
  (inotify, задержка ~2 с). Добавили файл на icloud.com — он появился локально
  (поллинг, по умолчанию каждые 30 с).
* **Фото — только скачивание, и только пополнение.** Медиатека «Фото» выгружается в
  `Photos/ГГГГ/ММ/` оригиналами (HEIC/JPEG/MOV как есть). Удаление снимка в облаке
  локальную копию не удаляет — см. [«Фото: архив, а не зеркало»](#фото-архив-а-не-зеркало).

```
~/iCloud/
├── Drive/          ← двусторонняя синхронизация с iCloud Drive
├── Photos/2026/08/ ← только скачивание, удалений не бывает
└── .icloud-synk/
    ├── state.json  ← база синхронизации
    └── trash/      ← сюда попадает то, что удалили в iCloud Drive
```

## Важно понимать до установки

У Apple **нет** публичного API iCloud для Linux: CloudKit Web Services даёт доступ только к
контейнеру собственного приложения, но не к пользовательскому Drive и не к медиатеке.
Поэтому программа работает через тот же приватный веб-API, что и сайт icloud.com
(SRP-логин на `idmsa.apple.com`, затем сервисы `drivews` / `docws` / `ckdatabasews`) —
подход, много лет используемый pyicloud и icloudpd. Следствия:

* Apple может изменить эти эндпоинты без предупреждения — тогда потребуется правка кода.
  Всё, что зависит от версии протокола, собрано в `internal/icloud/client.go`.
* Пуш-уведомлений об изменениях в облаке нет, отсюда поллинг.
* Слишком частый поллинг Apple может воспринять как абьюз — по умолчанию 30 с и
  экспоненциальный backoff до 15 минут при ошибках.
* Загрузка **в** медиатеку «Фото» не поддерживается сознательно: приватный CloudKit
  asset-upload не документирован и способен повредить библиотеку. Файлы, положенные
  руками в `Photos/`, программа не трогает и никуда не отправляет.

## Фото: архив, а не зеркало

Папка `Photos/` только пополняется. Ни одного пути, удаляющего файл из неё, в программе
нет: проход по медиатеке перебирает то, что iCloud отдаёт, и скачивает отсутствующее
(`internal/synk/photos.go`). Флаги `delete_remote` / `delete_local` относятся
исключительно к `Drive/` — сверка удалений работает по нему и папку `Photos/` не видит.

Что из этого следует:

* **Удалили фото в облаке (или на iPhone) — локальный файл остаётся.** Медиатека Apple
  вычищает «Недавно удалённые» через 30 дней, а ваша копия живёт дальше. Это и есть
  задумка: локальная папка служит архивом, из которого ничего не пропадает само.
* **Удалили файл из `Photos/` руками — он не будет скачан заново.** Снимок помечен в
  `state.json` как полученный, и повторная загрузка происходит только если сам ассет
  изменился в iCloud (сменился checksum). Чтобы вернуть удалённое, уберите
  соответствующую запись из `state.json` или сбросьте состояние.
* **Разбирать `Photos/` можно свободно** — переименования и перекладывания программа
  не заметит и не откатит.

## Установка

### Готовый бинарник (Go не нужен)

К каждому [релизу](https://github.com/kolesnikav/icloud-synk/releases) приложены статические
сборки без CGO для `linux/amd64` и `linux/arm64`:

```bash
curl -fsSL https://github.com/kolesnikav/icloud-synk/releases/latest/download/icloud-synk-linux-amd64.tar.gz \
  | tar -xz --strip-components=1 -C /tmp icloud-synk-linux-amd64/icloud-synk
install -Dm755 /tmp/icloud-synk ~/.local/bin/icloud-synk
icloud-synk version
```

Внутри архива также лежат `icloud-synk.service` и оба README. Рядом с архивами есть
`SHA256SUMS` для проверки:

```bash
sha256sum -c SHA256SUMS --ignore-missing
```

### Из исходников

```bash
git clone git@github.com:kolesnikav/icloud-synk.git && cd icloud-synk
make build              # bin/icloud-synk
make install            # ~/.local/bin/icloud-synk
```

Либо напрямую через Go:

```bash
go install github.com/kolesnikav/icloud-synk/cmd/icloud-synk@latest
```

Требуется Go 1.25+ для ограничения файловых операций корневым каталогом. Зависимости: `fsnotify` и `x/sys`.

## Первый запуск

```bash
icloud-synk login --dir ~/iCloud
```

Спросит Apple ID, пароль (эхо в терминале отключено) и шестизначный код 2FA.
Пароль **не сохраняется**: на диск ложится только сессия и trust token
(`~/.config/icloud-synk/session.json`, права 0600), которого хватает примерно на 30 дней.

### Если код 2FA не пришёл

Apple **никогда не присылает код на почту**. Варианты, где его взять:

* На iPhone/iPad/Mac появляется окно «Вход в учётную запись Apple ID…» — код показывается
  **только после нажатия «Разрешить»**. Если нажали «Не разрешать», уведомление не повторится.
* Надёжнее сгенерировать код самому, без уведомлений:
  **Настройки → [ваше имя] → Вход и безопасность → Двухфакторная аутентификация →
  Получить код проверки** (на Mac — «Системные настройки»).
* В приглашении `Two-factor code:` работают команды:
  * `sms` — отправить код SMS на доверенный номер (`sms 2` — на второй номер из списка);
  * `push` — повторно отправить запрос на доверенные устройства;
  * `q` — отменить вход.

Программа сама печатает, сколько доверенных устройств и какие номера доступны.
Код принимается и с пробелами (`123 456`).

Сначала — «холостой» прогон, чтобы увидеть план без изменений:

```bash
icloud-synk sync --dry-run
```

Затем одиночный полный проход:

```bash
icloud-synk sync
```

## Демон

```bash
make service     # копирует user-юнит, включает и запускает его
journalctl --user -u icloud-synk -f
```

Юнит пользовательский, а не системный: нужен доступ к сессионной шине для
`notify-send`. Чтобы демон работал и без активного входа в графику:

```bash
sudo loginctl enable-linger $USER
```

Когда trust token истечёт, демон не упадёт: он напишет в журнал, покажет уведомление
и будет ждать. Достаточно выполнить `icloud-synk login` в терминале — демон подхватит
новую сессию сам, перезапуск не нужен.

## Команды

| Команда | Что делает |
|---|---|
| `icloud-synk login [--dir PATH] [--apple-id ID]` | вход, запись конфига и сессии |
| `icloud-synk sync [--dry-run] [--drive\|--photos]` | один проход и выход |
| `icloud-synk daemon [--poll 30s]` | постоянная синхронизация |
| `icloud-synk status` | Apple ID, срок сессии, счётчики, проверка связи |
| `icloud-synk config` | эффективная конфигурация |
| `icloud-synk logout` | забыть сессию (папку и состояние не трогает) |
| `icloud-synk version` | версия сборки, платформа и версия Go |

Флаг `--verbose` включает отладочный лог у любой команды.

`verify-drive` сравнивает содержимое обычных файлов и отдельно перечисляет
пропущенные внутренние артефакты. Удалённые резервные копии со строгим именем,
создаваемым программой, могут пропускаться без записи происхождения, как при
синхронизации. Такие строки явно отмечены `provenance unavailable, ownership not
established`. Это не подтверждает владение файлом и не разрешает очистку копий.
Локальные копии этих файлов сравниваются; незавершённые операции и противоречивые
записи происхождения не обходятся проверкой имени. Счётчик `Files in iCloud`
показывает число файлов после исключения внутренних артефактов. Пользовательский
файл с точно таким служебным именем без записи происхождения неотличим от старой
копии; он явно указывается в отчёте. Подробнее: [проверка Drive](BACKUP_RETENTION.md#drive-verification).

## Конфигурация

`~/.config/icloud-synk/config.json` (создаётся при `login`, значения ниже — по умолчанию):

```json
{
  "apple_id": "you@example.com",
  "target_dir": "/home/you/iCloud",
  "sync_drive": true,
  "sync_photos": true,
  "poll_interval": "30s",
  "photos_interval": "15m",
  "debounce": "2s",
  "workers": 4,
  "delete_remote": true,
  "delete_local": true,
  "conflict": "both",
  "backup_retention": -1,
  "max_file_size": 0,
  "exclude": [".icloud-synk", ".DS_Store", "*.part", "*.crdownload", "*.partial",
              ".goutputstream-*", "~$*", ".~lock.*", "*.swp", "4913", ".Trash-*"],
  "notify": true,
  "password_command": ""
}
```

* `delete_remote` — локальное удаление отправляет файл в корзину iCloud.
* `delete_local` — удаление в iCloud переносит локальный файл в `.icloud-synk/trash/<дата>/`.
  Оба флага можно выключить: тогда удалённые файлы просто восстановятся с другой стороны.
  Оба касаются только `Drive/`; на `Photos/` они не действуют.
* `conflict` — `both` (сохранить обе версии), `newer` (побеждает более новая),
  `remote` (всегда версия из iCloud, локальная уходит в локальную корзину).
* `backup_retention` — `-1` (по умолчанию): хранить все резервные версии;
  `0`: перемещать подтверждённые резервные копии в корзину iCloud после проверки замены;
  положительное число: хранить N последних подтверждённых копий каждого файла.
  Значения меньше `-1` недопустимы. Старые копии без подтверждённого происхождения
  и незавершённые замены сохраняются. Подробнее: [backup retention](BACKUP_RETENTION.md).
* `exclude` — шаблоны сопоставляются с каждым сегментом пути.
* `password_command` — команда, печатающая пароль, для входа без терминала
  (например `secret-tool lookup service icloud`). Альтернатива — переменная
  `ICLOUD_PASSWORD`.

### Несколько независимых папок Drive

`drive_subfolders` позволяет синхронизировать несколько существующих папок
через один клиент, одну сессию авторизации и один процесс:

```json
{
  "target_dir": "/data",
  "sync_drive": true,
  "sync_photos": false,
  "protect_deletions": true,
  "drive_subfolders": [
    {"remote": "ExampleBackups", "local": "backups"},
    {"remote": "ExampleApp/widgets-data", "local": "widgets"}
  ]
}
```

`remote` задаётся относительно корня iCloud Drive, `local` — относительно
`target_dir/Drive/`. В примере создаются `/data/Drive/backups/` и
`/data/Drive/widgets/`, а состояние хранится в `/data/.icloud-synk/state.json`.
Обычные файлы доступных контейнеров приложений поддерживаются; пакеты iWork
по-прежнему не поддерживаются.

* Без `drive_subfolders` сохраняется прежнее поведение, включая `drive_subfolder`
  и ключи существующего состояния. Непустой `drive_subfolder` несовместим с
  `drive_subfolders`; пустой список соответствий запрещён.
* Пути должны быть непустыми, относительными, с разделителем `/`. Запрещены
  абсолютные пути, обратные слеши, двоеточия, NUL, пустые компоненты, `.`, `..`
  и пробелы по краям компонента. Повторяющиеся и вложенные друг в друга пути
  запрещены отдельно для локальных назначений и удалённых корней; сравнение
  выполняется без учёта регистра.
* Для нового режима символические ссылки в деревьях Drive и метаданных и их
  родительских каталогах вызывают ошибку. Запись Drive и сохранение состояния
  ограничены `target_dir`, в том числе при изменении путей во время передачи.
  Используйте обычные каталоги Linux и доверенные точки монтирования.
* Все удалённые деревья должны быть полностью прочитаны до применения плана.
  Недоступная, отсутствующая или неоднозначная папка либо неполный ответ API
  прерывают весь проход Drive. Удалённые корни автоматически не создаются.
* Защита удалений, `delete_local`, `delete_remote`, конфликты и хранение резервных
  копий действуют независимо для каждого пути. Обрабатываются только заданные
  локальные поддеревья. Dry-run показывает префикс локального назначения;
  сообщения проверки указывают удалённую и локальную папки.
* Старое состояние остаётся версии 1 с прежними ключами. В новом режиме
  добавляется поле `drive_mappings`, а ключи имеют вид `backups/file.txt`.
  Порядок соответствий можно менять. Добавление, удаление и изменение
  сохранённых соответствий запрещены: используйте новый `target_dir`.
  При переходе с заполненного старого состояния также нужен **новый каталог**;
  сохраните прежнюю копию и её состояние. Автоматического переосмысления или
  удаления старых записей нет. Старые версии программы не должны открывать
  состояние нового режима.

Пример Docker для Raspberry Pi 5: собирайте образ на Pi, храните конфигурацию
и сессию отдельно от данных:

```bash
docker build -t icloud-synk:local .
mkdir -p ./synk-config ./synk-data
# Сохраните JSON выше в ./synk-config/config.json (target_dir: /data).
# Заранее создайте удалённые папки через интерфейс iCloud.
# Для первых испытаний используйте запасной Apple ID.
docker run --rm -it \
  -v "$PWD/synk-config:/root/.config/icloud-synk" \
  -v "$PWD/synk-data:/data" icloud-synk:local login --dir /data
docker run --rm \
  -v "$PWD/synk-config:/root/.config/icloud-synk" \
  -v "$PWD/synk-data:/data" icloud-synk:local sync --drive --dry-run
docker run -d --name icloud-synk --restart unless-stopped \
  -v "$PWD/synk-config:/root/.config/icloud-synk" \
  -v "$PWD/synk-data:/data" icloud-synk:local daemon
```

Поддерживаются `sync`, `sync --dry-run`, `daemon` и `verify-drive`.
Остановите демон перед ручным запуском синхронизации с тем же каталогом.
Архитектура Docker не меняется.

## Как решается, что копировать (Drive)

Каждый проход сравнивает **три** источника: локальное дерево, дерево в iCloud и состояние
после предыдущего прохода (`state.json`). Без третьего источника отсутствующий файл
неотличим от удалённого.

| локально | в iCloud | в состоянии | действие |
|---|---|---|---|
| новый | — | — | загрузить в iCloud |
| — | новый | — | скачать |
| изменён | не изменён | есть | загрузить |
| не изменён | изменён | есть | скачать |
| изменён | изменён | есть | конфликт (см. `conflict`) |
| удалён | есть | есть | корзина iCloud |
| есть | удалён | есть | `.icloud-synk/trash/` |

«Изменён локально» = отличается размер или mtime; при совпадении размера дополнительно
сверяется SHA-256, поэтому `touch` не вызывает повторной загрузки. «Изменён в iCloud» =
изменился etag.

Конфликт при `conflict: both` выглядит так: побеждает более новая версия, проигравшая
остаётся рядом файлом `отчёт.conflict-2026-08-06T12-30-00.docx` и на следующем проходе
тоже уезжает в облако, так что ничего не теряется.

Для `Photos/` таблица не применяется: там всего два состояния — снимок уже скачан или
ещё нет.

## Чего программа не делает

* Не загружает фото и видео в медиатеку «Фото» (см. выше).
* Не удаляет ничего из `Photos/` — ни по команде из облака, ни самостоятельно.
* Не синхронизирует пакеты-бандлы iCloud (`.pages`, `.numbers`, `.key`): они
  пропускаются с записью в журнал.
* Не следует по символическим ссылкам — они пропускаются.
* Не переносит переименования как переименования: файл выгружается заново под новым
  именем, старый уходит в корзину.
* Не поддерживает совместное редактирование и историю версий iCloud.

## Разработка

```bash
make test    # юнит-тесты: SRP против независимого верификатора, сверка, сканер, состояние
make vet     # go vet + gofmt
make release # dist/: по архиву на платформу + SHA256SUMS (сначала прогоняет test и vet)
```

Релиз — это просто тег: `.github/workflows/release.yml` выполнит `make release` и выложит
архивы:

```bash
git tag -a v0.2.0 -m "icloud-synk v0.2.0" && git push origin v0.2.0
```

Структура:

```
cmd/icloud-synk/       CLI
internal/config/       конфигурация
internal/icloud/       клиент приватного API: SRP, сессия, Drive, Photos
internal/synk/         состояние, сканер, сверка, применение, демон
packaging/             systemd user unit
```
